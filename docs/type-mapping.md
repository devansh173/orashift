# Type-mapping policy

This is the contract DDL translations are graded against. When phase 3 verifies a
translated `CREATE TABLE`, it creates the table on PostgreSQL and compares the resulting
catalogue metadata to what this policy requires. A translation that runs but produces a
different column type is a **failure**, not a pass.

Measured against the pinned dialects: **Oracle AI Database 26ai Free 23.26.2.0.0** →
**PostgreSQL 17.10**.

## Numeric types

Oracle's `NUMBER` is a single decimal type with optional precision and scale. PostgreSQL
has distinct integer widths, so the mapping is driven by the declared precision.

| Oracle | PostgreSQL | Why |
| --- | --- | --- |
| `NUMBER(1)` used as a flag with `CHECK (c IN (0,1))` | `smallint` | Stays numeric. Mapping to `boolean` would change the values callers see and break `= 1` predicates |
| `NUMBER(p,0)`, `p` ≤ 4 | `smallint` | Max 9 999 fits in ±32 767 |
| `NUMBER(p,0)`, 5 ≤ `p` ≤ 9 | `integer` | Max 999 999 999 fits in ±2.1×10⁹ |
| `NUMBER(p,0)`, 10 ≤ `p` ≤ 18 | `bigint` | Max 10¹⁸−1 fits in ±9.2×10¹⁸ |
| `NUMBER(p,0)`, `p` > 18 | `numeric(p)` | Beyond `bigint`; must stay exact |
| `NUMBER(p,s)`, `s` > 0 | `numeric(p,s)` | Exact decimal preserved, scale for scale |
| `NUMBER` with no precision | `numeric` | Unconstrained exact decimal |
| `FLOAT`, `BINARY_DOUBLE` | `double precision` | Both binary floating point |
| `BINARY_FLOAT` | `real` | Single precision |

**Never map `NUMBER(p,s)` to `double precision`.** It is a binary float: it cannot
represent 0.01 exactly, so money arithmetic drifts. This is the single most damaging
mistake available in this mapping.

## Character types

| Oracle | PostgreSQL | Why |
| --- | --- | --- |
| `VARCHAR2(n)` | `varchar(n)` | Direct equivalent |
| `VARCHAR2(n CHAR)` | `varchar(n)` | PostgreSQL counts characters, not bytes, so the `CHAR` qualifier is already implied |
| `VARCHAR2(n BYTE)` | `varchar(n)` | Lossy in principle: `n` bytes of UTF-8 may be fewer than `n` characters. Acceptable here because the data is ASCII-dominant; a byte-exact migration would need `n` raised |
| `CHAR(n)` | `char(n)` | Both blank-pad to `n`. Mapping to `varchar` would silently change comparison semantics |
| `NVARCHAR2(n)` | `varchar(n)` | PostgreSQL databases in this project are UTF-8 throughout, so there is no separate national type |
| `CLOB`, `NCLOB` | `text` | Unbounded character data |
| `LONG` | `text` | Deprecated in Oracle; same target |

## Date and time types

| Oracle | PostgreSQL | Why |
| --- | --- | --- |
| `DATE` | `timestamp(0)` | **An Oracle `DATE` carries a time, to the second.** Mapping it to PostgreSQL `date` throws the time away |
| `TIMESTAMP(n)` | `timestamp(n)` | Direct equivalent |
| `TIMESTAMP(n) WITH TIME ZONE` | `timestamptz(n)` | Direct equivalent |
| `TIMESTAMP(n) WITH LOCAL TIME ZONE` | `timestamptz(n)` | Nearest available; the session-relative rendering is not reproduced |
| `INTERVAL YEAR TO MONTH` | `interval year to month` | Direct equivalent |
| `INTERVAL DAY TO SECOND` | `interval day to second` | Direct equivalent |

### The sub-second caveat on `DATE` → `timestamp(0)`

These two do not round the same way, which was verified on the pinned versions:

| Inserted value | Oracle `DATE` | PostgreSQL `timestamp(0)` |
| --- | --- | --- |
| `2024-05-17 10:30:45.7` | `2024-05-17 10:30:45` | `2024-05-17 10:30:46` |

Oracle **truncates** the fractional second; PostgreSQL **rounds** it. So the mapping is
exact only for values that are already whole seconds.

Mitigation in this project: the seed generator only ever emits whole seconds, so the
divergence cannot occur in the data. Any pipeline carrying real sub-second values would
need `date_trunc('second', …)` on the PostgreSQL side to match Oracle.

## Binary types

| Oracle | PostgreSQL | Why |
| --- | --- | --- |
| `RAW(n)`, `LONG RAW` | `bytea` | PostgreSQL has one variable-length binary type |
| `BLOB` | `bytea` | Same |
| `BFILE` | *out of scope* | An external file locator with no PostgreSQL equivalent |

## Identity and default values

| Oracle | PostgreSQL | Why |
| --- | --- | --- |
| `CREATE SEQUENCE s` | `CREATE SEQUENCE s` | `NOCACHE` → `CACHE 1`, `NOCYCLE` → `NO CYCLE` |
| `s.NEXTVAL` | `nextval('s')` | Function call rather than pseudo-column |
| `s.CURRVAL` | `currval('s')` | Same |
| `GENERATED ALWAYS AS IDENTITY` | `GENERATED ALWAYS AS IDENTITY` | Standard syntax in both |
| `GENERATED BY DEFAULT AS IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY` | Same |
| `DEFAULT SYSDATE` | `DEFAULT LOCALTIMESTAMP` | `SYSDATE` is the database server's local time, without a zone |
| `DEFAULT SYSTIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Both carry a zone offset |

## Constraints and indexes

Carried over unchanged, keeping the constraint names so metadata comparison is meaningful:

- `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`, `CHECK`, `NOT NULL`
- `CREATE INDEX name ON table (cols)`

Named rather than anonymous constraints are used throughout the reference schemas, because
phase 3 compares catalogue metadata and system-generated names (`SYS_C0010423`) are not
comparable across engines.

## Identifier case

Both engines fold unquoted identifiers, in opposite directions. Verified:

| Written | Oracle stores | PostgreSQL stores |
| --- | --- | --- |
| `CREATE TABLE CaseTest (MyCol …)` | `CASETEST`, `MYCOL` | `casetest`, `mycol` |

**Policy: never quote identifiers.** All schema objects are written unquoted and in
lower case, so each engine folds them to its own convention and every reference resolves.
Comparison of catalogue metadata is therefore case-insensitive. Quoting would force the
translation to carry Oracle's upper case into PostgreSQL, making every later query need
quotes too.

## Out of scope

Not translated by this project, and not present in the reference schemas:
object types, `VARRAY`, nested tables, `XMLTYPE`, `ANYDATA`, `ROWID`/`UROWID`, `BFILE`,
partitioning clauses, `ORGANIZATION INDEX`, and storage/tablespace clauses.
